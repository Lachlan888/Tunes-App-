# Prompt 34 — Session-first practice and compact responsive navigation

## Approved product brief

Source: direct user review of the 400 px mobile layouts on 24 September 2026, with an explicit clarification that the session-first Practice flow applies on desktop as well. These decisions are authorised implementation work for the runner. Preserve completed behaviour and user data; do not reinterpret this as a broad redesign.

**Goal:** Make Practice a direct, calm session journey; make Home the place for repertoire state; and remove repeated headings and avoidable vertical bulk from core mobile destinations.

**Scope:** Reuse the existing Next.js App Router, review scheduling, practice diary, learning queue, tune actions, account menu, shell header and responsive switchers. Do not create parallel practice queues, new repertoire state, duplicate actions or a second diary. The user owns manual functional testing and visual acceptance; use targeted automated behaviour/regression tests, scoped lint/typecheck and appropriate builds without manual browser walkthroughs or screenshot matrices.

## Product requirements

### 1. Practice opens the session

1. The primary Practice destination opens Focused Practice directly on desktop and mobile. Resume a genuine active session; otherwise begin with tunes due today.
2. A fresh session contains **today's due tunes only**. Do not silently mix catch-up tunes into that first queue.
3. When today's queue is complete, show a clear completion state. Offer **Continue with catch-up** as an explicit option; do not start catch-up automatically. When nothing is due today, show this completion state immediately.
4. Catch-up uses the existing overdue ordering and review machinery. It must not duplicate or mutate the learning queue beyond normal review outcomes.
5. Ending or completing a session leads into the existing diary/reflection journey. Prompt for the relevant session reflection after practice, not as a competing landing-page destination. Preserve safe dismissal/return behaviour and do not force a note when existing diary rules make it optional.
6. Remove the current Practice landing dashboard and its Review / Diary / Index / Focus areas switcher from the primary journey once equivalent destinations are available elsewhere.

### 2. Home owns repertoire state

1. Home becomes the location for the learning queue, currently in practice and known tunes/repertoire state. Reuse existing loaders and actions; do not copy tune membership or scheduling state.
2. Keep Home's Today / Repertoire / Social views. On mobile, remove the visible “Home views” label and the decorative spacer/gap above the switcher.
3. On mobile, place the switcher directly below the app header and keep it pinned while the selected Home view scrolls. It must not cover focused content or the mobile navigation dock.
4. Desktop Home may retain an appropriate non-sticky composition, but repertoire ownership and Practice routing changes apply at every viewport.

### 3. Deeper practice tools live in the menu

1. Add a clearly named, accessible Practice tools submenu to the account menu on desktop and mobile.
2. Include the existing Practice Diary, Focus Areas and tune index/history destinations, plus any other existing deep practice-management destination displaced by the old Practice switcher. Do not invent placeholder pages.
3. The submenu must support keyboard/touch use, communicate expanded and active states, and preserve direct URLs/back navigation.
4. Keep the primary Practice navigation devoted to starting/resuming Focused Practice. Do not restore a crowded Practice tab bar elsewhere.

### 4. Compact mobile tune rows

1. On the Tunes catalogue at mobile widths, make each tune result substantially more compact.
2. Keep title, key and time signature on one concise metadata line, truncating safely rather than causing horizontal overflow. Put the current learning/known/new status directly beneath it.
3. Present Preview, Add to List, Start Practice and Mark Known in one four-action row. Use concise labels/icons and responsive sizing as needed, but retain accessible names, disabled/pending states and existing action semantics.
4. Preserve clear tune-to-tune separation, keyboard focus, touch targets and selection mode without the current large card padding. Desktop catalogue layout is unchanged unless shared markup needs a neutral refactor.

### 5. Remove repeated mobile headings and pin view switchers

1. **Lists:** keep the shell header “Lists”; remove the duplicate page “Lists” heading and redundant “My Lists” heading. Put the existing list-view switcher directly below the app header and keep it pinned while content scrolls. The selected view begins with its primary action/search controls.
2. **Social:** keep the shell header “Social”; remove the duplicate page “Social” heading and “Friends views” label. Put Add friends / Activity directly below the app header and keep it pinned while content scrolls.
3. **Compare:** keep the shell header “Compare” and remove the duplicate page heading. Begin with the current state message and Compare actions.
4. These heading/switcher changes are mobile-specific. Preserve useful desktop hierarchy unless the shared shell already supplies the same duplicate heading there.
5. Sticky elements must have the correct top offset, background, stacking and focus/scroll margins. They must not overlap the account header, content, feedback affordance or navigation dock.
