# Prompt 33 — Curated festival hubs with controlled activation

## Approved product brief

Source: client discovery interview on 15 September 2026 in the festival planning task. User approved this scope and requested inclusion in the existing automation, with a developer festival-mode on/off control and festival selection. This is authorised implementation work for the runner; do not restart the discovery interview. The National Folk Festival 2027 is the first intended partnership. Artist names mentioned in the interview were examples, not confirmed programme bookings. Do not invent dates, participants, recordings, official endorsements or supplied branding.

**Goal:** Help musicians discover repertoire before a festival and find common tunes when playing together there. Browse artists, traditions and sessions first; follow an interest into an existing list and normal learning tools. Preserve a useful archive and reuse the same hub structure for future festival partnerships.

**Architecture:** Add a small event metadata and curation layer referencing existing public lists and canonical tunes. Reuse list creation/editing, tune contribution/reference tools, Save list/bookmarks, personal practice, authentication and Compare. There must be no festival-specific tune catalogue, copied list membership, parallel list editor, save mechanism, practice queue or Compare engine. Festival associations describe and order existing content, not own another copy of it.

**Stack:** Existing Next.js App Router, React, TypeScript and established database/auth patterns. No new framework or event service. Inspect present contracts before deciding the minimal schema. Follow RUNNER permissions, including its narrowly authorised migration exception only when required.

## Visitor experience

1. A modest, branded Home feature links to the selected festival hub. Use organiser-provided assets when available, with a clean text fallback. Preserve existing Home content and the six primary navigation destinations. No permanent Festivals tab, new Lists section, site-wide festival theme or additional floating controls.
2. A stable address such as `/events/national-folk-festival-2027` is the common destination for the festival mailing list and general QR posters. Support the link; creating/sending campaigns, printing posters and generating session-specific QR codes are outside this prompt.
3. The hub features artist collections and programmed sessions, with tradition labels and a simple editorial order. It is exclusively curated by the app owner from the festival programme and contributor material. No attendee submissions, organiser accounts, ticketing, recommendations engine or real-time programme integration. A session schedule lives only within each festival hub, as described below.
4. Artists/session leaders can supply just tune names. The owner uses existing tools to match canonical tunes, create missing entries and attach useful learning recordings. Exact performance versions and artist approval of references are not required. Do not impersonate an artist account or imply the reference recording is their performance. Allow accurate curator/leader display credits independent of the technical list owner and optional existing profile links.
5. Artist collections can stand alone. Sessions add leader names, location, published date/time, relevant timezone, a programme link and the programme snapshot date. Store only supplied details; allow unpublished/unknown details gracefully. A session references existing lists and remains an informal playing opportunity, not a fixed setlist.
6. Use friendly visible wording such as “Some tunes to get familiar with before joining in. Every session takes its own direction.” Label times as programme information at the recorded snapshot and link to the official programme for changes. Do not promise that tunes will be played, that artists will attend an informal jam, or that this is a live schedule.
7. Published hub content and linked public lists are browsable without signing in, including learning references permitted by existing visibility/provider rules. Use existing reference components and lifecycle controls. Private or removed lists/media must never be exposed through a festival association.
8. Save list uses the existing save/bookmark operation and its normal semantics. Sign-in/sign-up is requested when saving or invoking personal actions, preserving a safe return to the relevant public list/hub and clear continuation. Do not silently copy lists, bulk-mark tunes known or start practice. Repeated saves, already-saved states, failed saves and reloads behave as they do in normal Lists.
9. Include a meaningful contextual link to existing Compare, for example “Met someone to play with? Find tunes you both know.” Explain its immediate use in a session bar and route into the normal in-person/friend flow, retaining all existing identity, privacy, invitation and consent rules. No automatic comparisons, contacts or invites and no festival-specific Compare protocol.
10. After the event the hub can be archived at the same stable address, preserving selected repertoire and programme snapshot context. It records material shared for the festival, not proof of what happened or was played. Existing saved lists continue working. Future festivals get separate metadata/associations and stable addresses without hard-coded National logic.

## Session schedule within the festival hub

User clarification: include a day-by-day session schedule inside the festival hub only. When the programme is released, the owner can provide a photograph to the assistant, which prepares draft session entries and matches the existing curated lists. This does not require building an in-app AI/OCR upload service. Use the owner management workflow to enter reviewed extracted details; provide a documented structured batch-import path if needed to avoid repetitive entry, using the same validated session action rather than a second writing mechanism. No programme photo was supplied during planning: implement using disposable examples, not fabricated real programme data.

The hub offers a clearly labelled Sessions view/day selector, ordered by published local start time, showing session title, leader, venue and linked repertoire collections together. Show end time only when provided; handle overlapping sessions, sessions without a list, and unknown times without inventing them. Use actual festival-local dates/timezone so a visitor in another timezone sees the published day and time. Session cards with lists link directly to existing public list pages and existing Save list flow. A simple chronological day list is sufficient; no full timetable grid, app-wide schedule destination, calendar product, attendance tracking or live “happening now” claim.

Photo preparation extracts only visible information. Retain source/snapshot date and mark unclear names, times, dates and ambiguous list matches for owner review before publication. Never guess an illegible time or silently link similar names. Allow corrected/changed/cancelled sessions and list associations through owner editing without deleting source lists; show supplied cancellation status clearly. The page explains that it is a programme snapshot and links to the official programme for updates. Keep the friendly reminder that tune lists are suggested repertoire, not guaranteed setlists. Programme intake can remain assistant-assisted outside the app; do not require external OCR accounts or introduce a new model dependency.

## Owner management and safe launch controls

Use the existing protected Dev area (`app/dev/page.tsx`, `app/dev/layout.tsx`) and app-owner authorisation (`getAppAdminRole` in `lib/auth/roles.ts`). Only the app owner manages festival content/settings; a moderator, ordinary user or non-owner admin must not gain these writes. Enforce every read of draft content and every write on the server and in the database where relevant; hiding a control is insufficient. No additional organiser permission system.

Provide a compact Festival panel containing:

- **Festival mode: Off / On**, persisted for the app, default **Off**.
- **Selected festival**, persisted and chosen from owner-managed hubs. Selecting one does not publish it or enable mode. No selection is valid while off; enabling without an eligible published festival is rejected with a useful message.
- **Manage / Preview** the selected hub. Reuse established form/asset patterns for name, stable slug, description, supplied branding, programme URL/snapshot details, lifecycle state, editorial order, curator/tradition/session metadata and existing public-list associations. Link to the normal list editor to change tunes. Attach/detach/reorder list references without mutating source membership or visibility.
- Explicit **Draft / Published / Archived** lifecycle actions separate from Home promotion. New hubs start Draft and are visible only to the owner in authenticated preview. No public route, API response, metadata, discovery result or cached response may disclose draft content. Unknown or unpublished public URLs use the normal not-found response.

Festival mode governs the active Home promotion, not publication or deletion. Off produces the normal Home with no reserved space or festival navigation. It removes the promotion even for a previously selected festival; it does not erase saved lists or revoke deliberately published public hub/archive links. This distinction must be clear in the Dev panel so Off is not mistaken for unpublishing. Published and archived hubs remain directly accessible; explicit return to Draft withdraws public access. Archiving a selected festival removes its Home promotion; selecting another festival must never redirect an old hub URL to the new event.

Safe initial delivery: mode Off, no selected festival, no automatically published or archived production hubs. Allow owner-only preview while Off. The automation must not enable production mode, publish real content or install fabricated real-world artist/session data. Use disposable fixtures for acceptance. A missing/failed configuration read must omit the Home promotion and return safe states without breaking the rest of Home. Prevent stale cached banners/content following mode changes, selection changes, publication withdrawal, list visibility changes and archive transitions. Never cache owner draft responses as public data.
