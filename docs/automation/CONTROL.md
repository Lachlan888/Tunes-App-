# Lean runner controls — authorised 22 September 2026

## User testing preference — 23 September 2026

The user owns manual functional testing and visual acceptance across the project. Agents should test code using targeted automated behavioural/regression tests, scoped lint, typecheck when appropriate, and required code/build/database integration checks. Do not visually crawl the app, run manual browser walkthroughs, capture screenshot matrices, or request role-login fixtures for manual acceptance unless the user explicitly asks. This instruction supersedes older browser/manual/responsive visual acceptance gates in chunk specs, RUNNER and CONTROL. Record these checks as user-owned/not agent-verified, never as passed; their absence must not block the queue or pause the runner. Continue fixing demonstrated defects and preserve automated permission/privacy enforcement checks. At integration/release gates report code verification separately from user-owned manual acceptance; do not claim complete user-facing acceptance without user confirmation. Keep verification focused to reduce token use.

This protocol supersedes old one-slice-then-stop, every-run blocker recheck and scheduler-memory instructions in prompts, slices, plans and older results. Preserve product acceptance and all permission boundaries. No subagents by default.

## Preflight before context

After applicable AGENTS instructions, run `python3 docs/automation/control.py preflight` as the first project operation. Read its single JSON result. Do not combine this command with server startup or further shell commands. Exit code 10 means no immediate implementation; exit 2 means a real helper error to diagnose narrowly. Never continue on a failed acquisition.

- `ready`: acquire with `python3 docs/automation/control.py acquire --task ACTUAL_TASK_ID`. Only `acquired` grants ownership; retain its generated `run_id`. Then read RUNNER, state, current specification and (for Media) CONTRACT once. Read other files only as needed. Re-read state after acquiring, because another owner may have advanced it.
- `inspect_owner`: make one compact `wait_threads(timeoutMs=0)` status query for the returned owner. A latest `inProgress` turn means stop quietly. A fresh terminal latest turn (`completed`, `interrupted`, `failed`, `cancelled`) with no newer active turn is recoverable; interrupted turns need no completion timestamp. Archive/recover using `control.py recover --task OWNER --sha256 RETURNED_HASH --terminal-status STATUS --evidence 'tool name, turn ID and observed terminal status'`, then acquire. The helper checks that owner and lock contents have not changed. A `notLoaded` task is not itself running or abandoned: inspect its latest turn. If wait_threads gives no owner result, use one bounded read_thread call. Never read entire task history. A running detached mutating command must finish or be safely stopped before recovery; an idle dev server alone does not own the agent lock.
- If ownership genuinely remains unknown after those bounded checks, preserve the lock, report the specific unresolved owner once, and pause only this runner pending resolution. Never spend successive hourly invocations repeating the same ambiguous ownership investigation. Do not pause for ordinary live-owner contention; simply return. Do not delete a lock merely because it is old. Helpers' short-lived PIDs do not identify the agent owner.
- `cooldown` or `awaiting_input`: consult only the exact checkpoint and dependency queue to see whether independent ready work exists. If so, acquire with `--resume-reason independent-work`, preserve the blocked item, and select only a truly dependency-ready item. Otherwise exit quietly during a transient cooldown, or pause this runner if human input is required. With actual new input or changed environment, acquire with the appropriate `--resume-reason input-received` or `environment-changed`, then clear only the affected retry entry. Time passing is not permission.
- `complete_pause`: pause this automation using scheduler.json and the automation tool, preserving its other fields. Do not reopen completed work.

Before any edit, and at least every five minutes while working, refresh ownership with `control.py heartbeat --run RUN_ID`. A mismatch means stop edits immediately. Checkpoint before stopping and always `control.py release --run RUN_ID` during cleanup. Release stops if the lock belongs to another run. Use this helper for all runner lock writes. External tasks editing these repositories must coordinate with the same lock.

## Bounded batches and recovery

Hourly schedule, maximum 40 minutes, reserve the final five minutes for verification/checkpoint/cleanup. Complete up to three related small dependency-ready chunks/slices, one at a time. Checkpoint and verify each before continuing. Stop earlier if there is no useful work; this is a ceiling, not a quota. Never begin a slice that cannot reasonably fit. Split genuinely oversized work before editing, but do not create separate invocations for a tiny setup/checkpoint that fits the same batch. Do not batch through a major integration/release gate.

Dirty files, a moved HEAD, an interrupted turn, a missing commit or a previous failed tool attempt are not automatic project-wide blockers. Reconcile only overlapping files/hunks. Preserve unrelated work and adopt coherent prior implementation and dated verification. Recover pending commit bookkeeping from the actual commit/diff evidence without retesting an unchanged implementation. Never reset, stash or discard user work. Do not confuse absent tools with missing user authorisation; use another available authorised tool where appropriate. Explicit approval denials still require their stated approval and must never be bypassed.

On a genuine blocker, save the precise missing condition and minimal recheck in state. Keep the criterion pending. Record a stable non-secret fingerprint with `control.py defer --run RUN_ID --item ITEM --kind transient --fingerprint CODE`. After an actual failed recheck, retries back off 1 hour, 4 hours, then 24 hours. Repeated invocations during cooldown do not extend it. Use `--kind input` for required human input; do not retry that automatically. Use `control.py clear --run RUN_ID --item ITEM` after the condition resolves. If a prerequisite is unavailable, continue independent dependency-ready work within the batch; do not mark the blocked prerequisite passed. Never route around genuine acceptance dependencies.

## Small context and evidence

State is authoritative. Do not read scheduler memory during normal startup or append progress history there. Scheduler memory is a static pointer under 1 KB. Keep one concise append-only history entry per productive batch, with per-slice result IDs; do not write repeated lock-skip/cooldown entries, state timestamps or duplicate reports. Announce only meaningful progress, new blockers, required input or completion. Keep state/checkpoint under roughly 4 KB; put detail in the specific result. Keep retry.json limited to unresolved blockers and clear resolved entries.

Inspect branch/HEAD once. Get a compact working-tree summary, then active-file paths/diffs. Avoid dumping whole repository status or source files when targeted sections suffice. For safe owned-only commits, inspect full status programmatically but output only conflicts/relevant paths. Read the contract once per batch and relevant source requirements once. Use existing fixtures. Store full test output in the current evidence file and return counts plus relevant failures, not hundreds of passing lines. Reuse tool discovery during the batch; no deployment/telemetry/provider polling without a concrete active requirement.

## Verification that follows changes

- Content-only edits: scoped schema/mapping/publication checks and editorial review. No app build/browser run unless rendering/routing or an explicit acceptance criterion changed.
- Isolated code: affected behavioural tests and scoped lint; focused browser verification for changed interactions.
- Shared contracts/types: relevant consumers and typecheck. Auth, permissions and persistence retain required real database/role/transaction checks. Build-system/dependency/configuration risk may require an immediate build.
- Full appropriate suites, typecheck/lint, production build and broader browser/provider acceptance remain mandatory at named integration/release gates. Do not repeat them at each ordinary slice or simply because a new invocation began.
- Carry forward a pass only if relevant source, tests/fixtures, dependency/configuration and environment inputs have not changed. Record date, command and input scope in the result; include content hashes where carrying across invocations. HEAD alone is not sufficient for dirty worktrees. Do not use a whole-repository fingerprint that invalidates unrelated evidence. Rerun when scope is uncertain or risk warrants it. Never describe old evidence as newly tested.
- No scheduled deployments. For separately authorised deployment verification, follow only the specific deployment ID with bounded backoff and stop on terminal status; no ongoing background polling from builders.

## Scheduler operations

Use scheduler.json to identify only this automation. On completion or genuine human-input/unknown-owner suspension, read its current automation definition and update its status through the automation tool, preserving model, prompt, project, schedule and notification policy. Never pause another task or reset usage. The user can resume after supplying the missing input. Routine live-owner contention exits without pausing. These are scheduled tasks, not goal status changes.
