# P31-a — Readable invite aliases

Accepted 24 September 2026.

Implemented three-word musical invite aliases while preserving the existing 32-byte opaque token for QR codes and shared links. The curated 96-word vocabulary yields 884,736 aliases for the unchanged 10-minute lifetime. Inputs normalise case, repeated spacing and hyphens to one canonical lookup key. Invite creation stores the readable label/key, retries unique collisions up to six times, and regenerating still revokes the prior pending invite. Existing token-only rows remain valid; a pending legacy row is replaced with an aliased invitation when its host resumes it.

Both preview and acceptance resolve aliases server-side, then reuse the existing token-hash acceptance RPC. This preserves expiry, revocation, single-consumption, authentication, profile consent and connection behaviour for the same invitation reached through either words or its opaque link.

Database migration `20260924060600_readable_compare_invite_aliases.sql` was applied to the linked Tunes App project as remote version `20260924061139`. Remote catalog verification confirmed nullable legacy-compatible columns, the paired-value check constraint, unique alias index and RLS still enabled. Fresh security advisors reported no `compare_invites` findings; existing unrelated advisor findings remain outside this slice.
