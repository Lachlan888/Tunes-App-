# V02-06 — Integrated visual and functional parity gate

## Priority and dependency

Depends on `V02-05`. This is part of the **first-priority V02 visual gate**; P35-03 and feature work wait for V02-06. Follow `CONTROL.md` lock and bounded-batch rules, the product contract, and `docs/design/EDITORIAL_SYSTEM.md`. The V01 result is an initial code pass, not visual acceptance.

## Work

Revisit the complete V02-01 route/state inventory after implementation. Render-check every reachable user-facing route at narrow phone and desktop, with tablet and wide desktop representative layouts; inspect all distinct compositions and overlay states. Compare adjacent routes for exact palette jobs, heading scale, metadata order, wrapper depth, rules, radius, spacing, active navigation, focus/contrast and fixed-control overlap. Resolve inconsistencies, then recheck corrected routes. Document screenshots or precise rendered observations, remaining inaccessible states, and all existing actions/URLs/data flows retained. Run relevant automated tests, typecheck, lint and production build. Do not mark complete from code inspection or build alone. Owner final manual acceptance remains separate.

Return explicitly to the owner-supplied desktop-rail and account-menu starting points. Recheck every screenshot-visible route/overlay plus the source-derived inventory, and document whether the original active/hover ambiguity, tooltip overlap, menu hierarchy/rules, top-level active states, disclosure behavior, floating placement and attention-badge balance are resolved.

## Acceptance evidence

- Implement the visual treatment in actual route/component code, preserving routes, data flows, actions, keyboard/screen-reader access, and useful information. Do not substitute a plan or blanket CSS override for route-level corrections.
- Record a route-by-route checklist of rendered states and widths, defects found, changes made, and rechecks. Check no eyebrow above the single dominant title; no ordinary nested cards; semantic palette and contrast; consistent rows/rules/radius/type; responsive mobile and desktop compositions with equal capability.
- Use local or disposable environments for rendered checks; no production mutation. Record inaccessible states as unverified, not passed. Owner final manual acceptance is separate.
- Run checks appropriate to affected code. Save the exact results and remaining work in `docs/automation/results/V02-06.md`; advance state only after acceptance evidence exists.
