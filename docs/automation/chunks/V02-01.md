Depends on `V01-editorial-visual-system`. This is part of the **first-priority V02 visual gate**; P35-03 and feature work wait for V02-06. Follow `CONTROL.md` lock and bounded-batch rules, the product contract, and `docs/design/EDITORIAL_SYSTEM.md`. The V01 result is an initial code pass, not visual acceptance.

## Work

Inventory all `app/**/page.tsx` routes plus shared dialogs, menus, empty/loading/error and overlay states. Make a route/state/viewport checklist in this result, assigning every route to V02-02 through V02-05 (include internal/moderator surfaces). Audit and fix shared `app/globals.css`, shell/navigation, headers, rows, controls, material tokens and wrappers. Remove broad CSS disguises only when equivalent component styling is in place. Establish one consistent title scale, rules, radii and state palette. Render-check shell and one representative route at narrow phone, tablet and desktop. Preserve all behavior.

Begin with the owner's 4 October desktop-rail and account-menu screenshots, but treat them only as starting evidence. Inspect `DesktopNav`, `NavigationDock`, `AppHeader`, `AccountMenu`, the account trigger and floating placement. Trace Home, Practice, Tunes, Lists, Social, Compare and the conditional Festival hub preview; Account & settings, Setlists, Badges, Trends, all Practice tools destinations, Inbox, Metronome, Help & feedback, conditional Moderator/Developer tools, and Logout. Follow route links into nested detail/edit/secondary states—especially tune Info/Reference, list and setlist reader/owner/edit states, and Diary/Focus/Tune index—and inventory event-driven Metronome and feedback overlays separately. Check current/hover/focus ambiguity, attention-badge salience, tooltip overlap, active states, disclosure keyboard behavior, clipping/scrolling, rule density and purposeful floating-surface treatment. The screenshots do not replace the full route/source inventory.

## Acceptance evidence

- Implement the visual treatment in actual route/component code, preserving routes, data flows, actions, keyboard/screen-reader access, and useful information. Do not substitute a plan or blanket CSS override for route-level corrections.
- Record a route-by-route checklist of rendered states and widths, defects found, changes made, and rechecks. Check no eyebrow above the single dominant title; no ordinary nested cards; semantic palette and contrast; consistent rows/rules/radius/type; responsive mobile and desktop compositions with equal capability.
- Record the screenshot observations separately from later live rechecks so a starting-point image is never reported as post-change acceptance.
- Use local or disposable environments for rendered checks; no production mutation. Record inaccessible states as unverified, not passed. Owner final manual acceptance is separate.
- Run checks appropriate to affected code. Save the exact results and remaining work in `docs/automation/results/V02-01.md`; advance state only after acceptance evidence exists.
